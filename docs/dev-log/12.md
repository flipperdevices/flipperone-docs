### Write your own

A FlipCTL app can be a single Python or JavaScript file. The "Hello World" example comes in two forms: a script in [Python](https://github.com/flipperdevices/flipctl-slint/blob/5407d490a73dd7e3f95d4302c5fe1fbea525aa90/docs/apps.md#L157-L189) or [JavaScript](https://github.com/flipperdevices/flipctl-slint/blob/5407d490a73dd7e3f95d4302c5fe1fbea525aa90/docs/apps.md#L193-L224), a counter with a progress gauge in about 30 lines, and a [Rust app](https://github.com/flipperdevices/flipctl-slint/tree/HEAD/apps/hello) that adds a second page showing how to draw your own picture on the 256×144 screen. You say what the rows are and what the keys do, and FlipCTL takes care of the window, the keys, scrolling and closing. Copy your file into `~/Apps` on the device and it appears in the app list. It runs once the Python or JavaScript Runtime is installed from the App Manager. We reworked the scripting API this week and moved every built-in script to it. The [apps guide](https://github.com/flipperdevices/flipctl-slint/blob/HEAD/docs/apps.md) has the rest.

### A native engine underneath

These apps run on a native FlipCTL engine that we've started building in Rust with the Slint toolkit, in the new [flipctl-slint](https://github.com/flipperdevices/flipctl-slint) repository. When we introduced FlipCTL in [our blog post](https://blog.flipper.net/flipctl-our-gui-framework-for-embedded-linux-systems/), its screen was drawn by a web engine. The native one is in progress, and the build needs only three system libraries.

## Fixing firmware without a board

You don't need a Flipper One to improve its firmware. Our community contributor @hypery11 ran our firmware in an RP2350 emulator with a model of the INA219 power monitor, and [discovered a configuration bug](https://github.com/flipperdevices/flipperone-mcu-firmware/pull/268). On one board, the chip was set up with a smaller measuring range than intended, which clipped the current reading at 4 A. In the emulator, a 6 A load now reads 6.0 A instead of 4.0 A. This is the chip behind the Power Meter we showed in [Dev Log #11](./11.md#how-the-built-in-power-meter-works).

The same emulator, this time with a model of the LED power chip, helped @hypery11 [take up to 15 ms of blocking out of the MCU's LED event loop](https://github.com/flipperdevices/flipperone-mcu-firmware/pull/271). Each time the LEDs changed, the firmware rewrote the chip that switches the LED power and waited 5 ms for every lit line, even when the line was already on. With all three lines lit, the event loop sat blocked for 15 ms. Now it skips both. In a test run of 29 LED updates, the writes to that chip dropped by more than half, and the redundant ones went to zero.

![Stacked columns of writes to the LED power chip in the same 29 LED updates. Board A: 40 writes before the fix, 26 of them redundant, and 14 after. Board B: 36 before, 22 redundant, and 14 after.](/files/pics/dev-log/12/led-controller-writes.png "Writes to the LED power chip in the same 29 LED updates, before and after the fix, in an emulator")

Thank you, @hypery11!

## More reliable Debug Probe UARTs

![Flipper One Debug Probe V1, a small board with labeled test pads for the CPU and the MCU, a debug header and a USB-C port](/files/pics/dev-log/12/flipperone-debug-probe.jpg "The Flipper One Debug Probe")

The [Debug Probe](../hardware/Debug-probe.md) is how we reach Flipper One without taking it apart: it connects behind the back plate and gives your PC four USB serial ports (the Linux console, the MCU command line, the MCU log and the probe's own command line), plus SWD debugging of the MCU and a GPIO bridge. It is part of the portable development kit from [Dev Log #9](./9.md).

This week, we fixed how the probe's serial bridges behave when your PC connects and disconnects. Each bridge now opens its UART when the PC connects over USB and releases it when the PC disconnects, so [every connection starts clean](https://github.com/flipperdevices/flipperone-debug-probe/pull/23). A send that can't complete because the PC has gone away now gives up and says so, so a bridge no longer waits for a "sent" signal that never arrives. That wait could leave the probe's own command line silent after a reconnect.

The fixes are on the `dev` branch. The latest release, v0.6.0, doesn't have them yet, but every push builds a firmware file you can download from the repository's [Actions](https://github.com/flipperdevices/flipperone-debug-probe/actions) tab, and the [Debug Probe page](../hardware/Debug-probe.md) shows how to flash it. The probe's hardware design and firmware are fully open, so you can also build your own.

## TV Media Box: Kodi on one display

With two displays connected, Kodi used to stretch across both, and the layout changed depending on which cable you plugged in first. Kodi now runs on the most recently connected display only. Unplug that display, and Kodi returns to the previous one. The same change installs the fonts Kodi's skin expects, so its text no longer falls back to a default font. See [issue #197](https://github.com/flipperdevices/flipperone-linux-build-scripts/issues/197) and [PR #201](https://github.com/flipperdevices/flipperone-linux-build-scripts/pull/201).

## GPIO USB pin labels — \[have your say\]

The USB pair on the GPIO header is labeled **UDP** and **UDN**, and it's easy to mistake them for power pins. We shared seven versions of the label, and the discussion is converging.

![The GPIO header with seven USB pin labelling options: the current UDP and UDN, and options 1 to 6 with different names and groupings](/files/pics/dev-log/12/gpio-usb-pins-options.png "Seven ways to label the USB pins on the GPIO header")

So far, most comments are in favor of the standard **D+** and **D-** names, with a frame or bracket labeled "USB" to group the pair. Option 4 has the most support. Still open: square or curved lines, whether the text says USB, USB 2.0 or USB DATA, and whether a USB trident, color or icon survives at silkscreen size.

Tell us which option you would pick and why in the [GPIO header USB pins design issue](https://github.com/flipperdevices/flipperone-ui/issues/11).

## Profiles and device identity — \[help wanted\]

Every Flipper OS profile has its own settings, so anything you set up in one profile, such as a user or a password, stays there, and the other profiles stay at factory defaults. On a device where one profile had been set up, the new user existed only there, and the factory login still worked in all five factory profiles. The weakest profile in the boot menu decides how secure the whole device is, and every profile shares the same home directory.

Before the first-run setup flow ships, we need to decide which parts of "who this device belongs to" stay in each profile, which follow the device, and how the second group reaches every profile. Our community is already prototyping answers:

- @miavuli has an [experiment for keeping the owner's password the same in every profile](https://github.com/flipperdevices/flipperos-btrfs-tools/pull/1).
- @rafaetri [keeps one set of SSH host keys for every profile](https://github.com/flipperdevices/flipperos-btrfs-tools/pull/2), so switching profiles doesn't make your SSH client warn that the host key changed.
- @overdeadsss opened a [prototype this week](https://github.com/flipperdevices/flipperos-btrfs-tools/pull/3) that shares one Wi-Fi country setting between profiles. It is meant to stop the Router profile's 5 GHz hotspot from falling back to 2.4 GHz, and the PR has the steps to try it if you have a board. Timezone and locale are harder, and are still open.

None of these is merged yet. If you'd like to take one on, or you have a better idea, join the [discussion](https://github.com/flipperdevices/flipperone-linux-build-scripts/issues/140).
