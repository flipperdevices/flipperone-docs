This is our Dev Log where we share how the development of Flipper One is going.

In this update: DisplayPort over USB-C gets a live demonstration, the display controller learns to adapt its refresh rate, and we’re improving the way Linux and the MCU work together.

## DisplayPort over USB-C is getting closer

One USB-C port can do more than carry data and power. With DisplayPort Alternate Mode, it can also send video to an external display.

On October 28, we shared a working demonstration of DisplayPort over USB-C on Flipper One, running an almost-upstream Linux kernel. We’re working on this together with Collabora, with the goal of bringing proper USB-C display output to Flipper One and other Rockchip RK3576 and RK3588 devices.

Making this work involves several parts of the Linux stack. USB Power Delivery first negotiates the connection, including which side provides power and which side acts as the host. It then discovers supported Alternate Modes. The USB-C controller and PHY route the high-speed lanes to the DisplayPort controller, which brings up the display link.

There are some interesting edge cases along the way. For example, changing the PHY configuration can interrupt an existing USB connection if it is done at the wrong time. A dock should not disconnect a storage device just because a display was plugged into the same dock. The implementation has to account for these interactions as well as display hotplug and link setup.

The work is progressing through upstream Linux review. Some of the PHY and display-controller changes were still under review when the demonstration was presented, and display modes can still have limitations.

## A display that adapts to what you’re doing

A display does not need to refresh at its maximum rate all the time. A static screen and a fast-moving animation have different requirements, and refreshing more often than necessary can waste work.

The adaptive refresh-rate work in the MCU firmware introduces several refresh steps: 10, 15, 30, 60, and maximum (approximately 115) FPS. The minimum is set to 30 FPS while Linux is running and 10 FPS in MCU mode.

The display driver also moves buffer copying from `memcpy` to DMA. In the measurements reported in the pull request, CPU usage at 65 FPS drops from 2.4% to 1.6%.

There is more to adaptive refresh than changing a number. The driver needs to handle frames arriving while a refresh-rate change is pending, avoid conflicting timer updates, and shut down cleanly while a frame is still in progress. The implementation includes safeguards for these cases.

The change is still under review, and power measurements across the different refresh rates remain important to understanding its real-world impact.

## Smoother handoff between RPC sessions and the CLI

The MCU and Linux communicate through several interfaces, and the developer experience depends on those interactions behaving predictably.

One recently proposed firmware fix addresses a small but frustrating issue: after a host closed an RPC session, the first character typed into the CLI could disappear. For example, typing `uptime` immediately after closing the session could result in the shell receiving `ptime`.

The root cause was in the read loop. It waited for data from a pipe, and the periodic state check did not interrupt that blocking read. The close request could therefore be handled only after another byte arrived.

The proposed fix uses a `FuriEventLoop` to handle incoming data and session closure as separate events. It also moves screen-stream cleanup into the session worker, preventing a late request from starting a stream after the session has already begun shutting down.

The contributor tested the change in an RP2350 emulator using the existing RPC test script. The reported checks include repeated session open-and-close cycles, typing a command immediately after closing, and closing a session while a virtual display request is in flight. Physical hardware testing is still outstanding.

**Visual proposal:** A simple before-and-after sequence diagram.

Before: - Host sends close request. - CLI read remains blocked. - Next character arrives and is consumed. - Shell receives the remaining characters.

After: - Host sends close request. - Close event wakes the session loop. - Session shuts down and returns to the prompt. - The next command remains intact.

**Visual details:** Use a short terminal recording showing the `uptime` command working immediately after an RPC session closes. Pair it with the sequence diagram so the audience understands why the fix matters.

## Giving each device a name

Flipper One combines a Linux CPU with an RP2350 MCU. Some device information needs to cross that boundary, and a stable hardware name can make devices easier to identify in software and manufacturing workflows.

An open MCU firmware change implements the MCU side of a unique-device-name feature. It stores a short name in the RP2350’s one-time-programmable memory and exposes it to Linux through the I²C interconnect.

OTP memory needs special care because programmed bits cannot simply be cleared and rewritten like ordinary storage. The proposed implementation writes the name data first and its metadata last. It then reads the value back to verify the result. If programming is interrupted before the metadata is written, the incomplete value is not treated as a valid name.

The change also adds a read-only unit test so the test can inspect OTP behaviour without programming the lab board.

The exact OTP layout and naming constraints are still awaiting confirmation, and the pull request notes that it has not yet been tested on physical hardware.
