In [Dev Log #10](./10.md), we showed you how to install Flipper OS on supported single-board computers (SBCs) and introduced the App Manager. Over the past two weeks, we landed the core pieces that turn Flipper OS into a self-updating system with a native application runtime. In this post, we'll show you how on-device OS and profile updates work, tour the first built-in FlipCTL apps, walk through writing and testing your own app (even without any special hardware), and share where we need your help next.

## Updating Flipper OS and its profiles right on the device

When you use a standard Linux SBC as an all-in-one portable tool, installing packages for a Wi-Fi router one day and tweaking configs for a media player the next, you eventually end up with a messy, broken system that is easier to wipe and reflash than to fix.

Our [OS profiles](../cpu-software/Flipper-OS.md) architecture solves this by separating the base operating system (OS) from task-specific Btrfs overlays like Desktop, TV Media Box, Wi-Fi Router, and Lab. The last holdout was the base OS itself: until now, a newer Flipper OS build meant reflashing from a computer. That changes now: you can update both the OS and your profiles directly on the device, without losing your data or apps.

### Incremental updates from the Settings app

We [added an Update Flipper OS option](https://github.com/flipperdevices/flipctl-slint/commit/92d49b2294514feffc2d71f648795bf8591610b0) directly to the Settings app in [`flipctl-slint`](https://github.com/flipperdevices/flipctl-slint) and connected it to the installer from [Dev Log #9](./9.md). To keep downloads small, our build scripts now [export only incremental profiles](https://github.com/flipperdevices/flipperone-linux-build-scripts/commit/e38d1b09b7e78984adc1ff59d44602f057ed26e5) using the Minimal profile as a shared base, while [`flipperos-installer`](https://github.com/flipperdevices/flipperos-installer) shows more accurate progress by giving [larger data transfers a greater share of the progress bar](https://github.com/flipperdevices/flipperos-installer/commit/20fb1953). Thank you to community contributor *@Gelules* for spotting the new archive filenames on our build server and opening [Issue #454](https://github.com/flipperdevices/flipperone-docs/issues/454), [Issue #455](https://github.com/flipperdevices/flipperone-docs/issues/455), and [PR #453](https://github.com/flipperdevices/flipperone-docs/pull/453) to keep our docs aligned.

Under the hood, the POSIX shell toolkit in [`flipperos-btrfs-tools`](https://github.com/flipperdevices/flipperos-btrfs-tools) handles these upgrades in place:

- `update-profile` [fetches build manifests in parallel](https://github.com/flipperdevices/flipperos-btrfs-tools/commit/d2934914), [streams Btrfs receive data directly during download](https://github.com/flipperdevices/flipperos-btrfs-tools/commit/4dd161a0), and supports `--every` for [scheduled update checks](https://github.com/flipperdevices/flipperos-btrfs-tools/commit/39a41c6eb8ece3265f0564346d964159b335f861).
- `migrate-profile --keep-identity` preserves your user identity, passwords, and SSH keys across profile builds, while `check-profile` reports one of five health states for each subvolume.
- `boot-profile` now [reads the M.2 slot mode from hardware strap pins](https://github.com/flipperdevices/flipperos-btrfs-tools/commit/336cd20c) rather than hardcoded values.

![Diagram showing incremental Btrfs streams updating Flipper OS profiles from the Minimal base while preserving user state and installed apps](/files/pics/Btfrs_profiles.jpeg)

To keep shared settings consistent across profiles ([Issue #140](https://github.com/flipperdevices/flipperone-linux-build-scripts/issues/140)), community contributors *@miavuli*, *@rafaetri*, and *@overdeadsss* have been prototyping identity sync tools. Huge thanks to *@overdeadsss* for submitting Wi-Fi country sync and home-folder recovery in [PR #3](https://github.com/flipperdevices/flipperos-btrfs-tools/pull/3), [PR #202](https://github.com/flipperdevices/flipperone-linux-build-scripts/pull/202), and [PR #204](https://github.com/flipperdevices/flipperone-linux-build-scripts/pull/204).

Because incremental updates keep your home folder and customizations intact across builds, any apps you install stay right where you left them — which brings us to the new apps running on Flipper One's screen.

## Meet the first native FlipCTL apps

In [`flipctl-slint`](https://github.com/flipperdevices/flipctl-slint), we have been replacing the early web-based graphical user interface (GUI) prototype from [Dev Log #10](./10.md) with a native Rust and Slint runtime for Flipper One's 256×144 screen, while [`flipctl-apps`](https://github.com/flipperdevices/flipctl-apps) hosts the App Manager catalog (`apps.toml`). Over the past week, `flipctl-slint` gained a bundled pixel theme, automatic top-bar drawing rules, a Python and JavaScript script engine, and our first five built-in utilities.

Select each tab below to see what the new apps do on the built-in display:

:::::Tabs
::::Tab{title="USB Analyzer"}
Ever picked up a random USB-C cable from your desk and wondered what it actually supports? Written as a FlipCTL Python script ([`usb-analyzer.fap.py`](https://github.com/flipperdevices/flipctl-slint/blob/dev/apps/Test%20Tools/usb-analyzer.fap.py)), the USB Analyzer names each port after the physical label printed on the Flipper One case via `udev`'s hardware database (`hwdb`) and reads the electronic marker (e-marker) chip sealed inside the cable plug.

At the kernel layer, we also expanded our `FUSB302` and `TCPCI` Type-C drivers with a [five-patch SOP' cable-plug communication series](https://github.com/flipperdevices/flipper-linux-kernel/commit/2896ede8fd52edc4a4e35f91b4b4ac1891425d99) over USB Power Delivery (USB-PD) and taught the Type-C Port Manager (TCPM) to [record partner Product Type Vendor-Defined Objects (VDOs)](https://github.com/flipperdevices/flipper-linux-kernel/commit/6ef48ffc).

## Write and run your first FlipCTL app

If you installed Flipper OS on an RK3576 board ([Dev Log #10](./10.md)), you can write and run your own FlipCTL apps today. Don't have an SBC yet? Community contributor *@Gelules* created [`gelules/qemu-flipperos`](https://github.com/gelules/qemu-flipperos) to boot an official Flipper OS image inside a QEMU virtual machine (VM) on a standard PC. While hardware-specific features are limited without an RK3576 processor or RP2350 microcontroller unit (MCU), it boots the Flipper OS userspace so you can test FlipCTL apps in a VM with zero extra hardware.

Our new developer guide in [`flipctl-slint/docs/apps.md`](https://github.com/flipperdevices/flipctl-slint/blob/dev/docs/apps.md#L149-L249) covers two ways to build an app:

1. **Single-file Python (`.fap.py`) or JavaScript (`.fap.js`) scripts:** Drop a script into `~/Apps` and the script engine automatically handles pages, keypad input, and clean exit hooks.
2. **Native Rust and Slint apps:** Build compiled binaries using the bundled theme in [`flipctl-slint`](https://github.com/flipperdevices/flipctl-slint) and package them for [`flipctl-apps`](https://github.com/flipperdevices/flipctl-apps).

### How to write and run a Hello World script app
:::::WorkflowBlock
::::WorkflowBlockItem
**Boot Flipper OS on an SBC or in QEMU**

Boot Flipper OS on a supported RK3576 board ([Dev Log #10](./10.md)) or in a VM using [`gelules/qemu-flipperos`](https://github.com/gelules/qemu-flipperos). Open the App Manager — which checks package sizes against [`flipctl-apps`](https://github.com/flipperdevices/flipctl-apps) limits before unpacking — and install the Python/JS Runtime.
::::
::::WorkflowBlockItem
**Create a `.fap.py` or `.fap.js` script in `~/Apps`**

Follow the [Hello World example in `docs/apps.md`](https://github.com/flipperdevices/flipctl-slint/blob/dev/docs/apps.md#L149-L249) and save your file in `~/Apps`. FlipCTL draws the system top bar automatically, so your script only defines its own pages and key handlers.
::::
::::WorkflowBlockItem
**Launch your app from the FlipCTL menu**

Your script appears automatically in the launcher. Open it to test your UI and keypad navigation — and check [`usb-analyzer.fap.py`](https://github.com/flipperdevices/flipctl-slint/blob/dev/apps/Test%20Tools/usb-analyzer.fap.py) to see how a multi-page hardware script is written.

## Catching MCU power and LED bugs in an emulator

QEMU isn't the only way community contributors are testing Flipper One without a physical board. Contributor *@hypery11* ran [`flipperone-mcu-firmware`](https://github.com/flipperdevices/flipperone-mcu-firmware) inside an RP2350 emulator to inspect Inter-Integrated Circuit (I²C) traffic and fixed two subtle hardware bugs:

- **Uncapping the INA219 sensor above 4 A:** Fixed a big-endian C bitfield mismatch in the configuration register that clipped Power Meter current readings at **4 A** ([PR #268](https://github.com/flipperdevices/flipperone-mcu-firmware/pull/268)).
- **Removing redundant LED writes and a 15 ms delay:** Fixed a state mismatch that re-initialized the LED controller and blocked the event loop for **15 ms** on every update ([PR #271](https://github.com/flipperdevices/flipperone-mcu-firmware/pull/271)), alongside our merge for individual service and battery-outline LED segment control ([PR #264](https://github.com/flipperdevices/flipperone-mcu-firmware/pull/264)).

![Chart comparing LED controller I2C register writes before and after PR #271](/files/pics/led-controller-writes.png)

Meanwhile, on the Linux side of the sleep handshake, *@overdeadsss* merged [PR #203](https://github.com/flipperdevices/flipperone-linux-build-scripts/pull/203) to fix a classic shell bug: our `system-sleep` hook tried to notify the MCU about suspend using a wildcard glob inside a file redirection, which `dash` (`/bin/sh`) silently refused to expand!

Whether you prefer writing high-level Python and JavaScript utilities for the 256×144 screen or hacking on low-level C and Device Trees, there are plenty of ways to contribute!

Now that single-file `.fap.py` and `.fap.js` scripts can wrap standard Linux command-line tools (like `ping`, `nmap`, `iperf3`, or `sensors`) and read hardware sysfs nodes directly from `~/Apps`, we'd love to see what utilities you come up with.

## Join Flipper One development and make your contribution

Flipper One is under active development. We welcome everyone who wants to test it, share feedback, and help shape its future.

- **Write a FlipCTL app or tackle a kernel challenge:** Check out the [FlipCTL app developer guide](https://github.com/flipperdevices/flipctl-slint/blob/dev/docs/apps.md), explore the catalog in [flipperdevices/flipctl-apps](https://github.com/flipperdevices/flipctl-apps), or jump into one of the five kernel tasks above.
- **Pick a task:** Browse the [🚧 Open tasks](https://docs.flipper.net/one/open-tasks) page for ways to contribute across all repositories.
- **Share your project:** Built something that helps test or improve Flipper One, like [`gelules/qemu-flipperos`](https://github.com/gelules/qemu-flipperos)? Add it to the [community projects](../community/community.md) page.
- **Contribute module & accessory 3D models:** Check out the [contribution guide](../mechanics/About-Mechanics.md#contribute-a-third-party-module) and open a pull request in [flipperdevices/flipperone-mechanics](https://github.com/flipperdevices/flipperone-mechanics).
